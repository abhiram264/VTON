# Weekly Post-Production Operations Runbook

This runbook defines the weekly operational review procedure for AI Fashion Vault in production per technical implementation plan §71.

The weekly operations review aggregates telemetry across the completed ISO calendar week (Monday 00:00 UTC through Sunday 24:00 UTC). It evaluates week-over-week (WoW) trends, executes AI regression benchmark gates, audits per-source retailer compatibility, evaluates user engagement and retention plumbing, and enforces unit economic discipline.

Where `docs/runbooks/DAILY_OPERATIONS.md` inspects same-day operational incidents and urgent alert escalations, this runbook governs week-over-week trend analysis, release-gate validation, and data-driven promotion recommendations.

---

## Operational Scope & Review Cadence

- **Review Cadence:** Executed every Monday at 09:00 UTC by the AI Operations On-Call Engineer.
- **Review Window:** The preceding completed ISO calendar week, defined as Monday 00:00:00 UTC through Sunday 23:59:59 UTC (Sunday 24:00 UTC).
- **ISO Week Tag Format:** `w%04d-%02d` (ISO week-based year and two-digit ISO week number, e.g. `w2026-36`), matching the format generated by `MicrometerProductMetrics.week()` using `java.time.temporal.WeekFields.ISO`.
- **Review Owner:** AI Operations On-Call Engineer (primary), with sign-off and promotion recommendations reviewed by the AI Platform Lead and Release Engineer.
- **Auditable Record:** All section verdicts, tier-2 benchmark run records, and release blockage findings are recorded in Section 8 of this runbook and committed to release audit logs.

## Bind Parameter Convention for SQL Fallbacks

All SQL queries in this runbook are read-only (`SELECT`) and parameterized with ISO week boundary timestamps.

```bash
# Example psql execution using bind parameters for ISO week w2026-36:
psql "$DATABASE_URL" \
    -v week_start="'2026-08-31 00:00:00+00'" \
    -v week_end="'2026-09-07 00:00:00+00'" \
    -v prev_week_start="'2026-08-24 00:00:00+00'" \
    -v prev_week_end="'2026-08-31 00:00:00+00'"
```

Alternatively, operators may substitute PostgreSQL dynamic date expressions:
- Current ISO week window: `(date_trunc('week', now() AT TIME ZONE 'UTC') AT TIME ZONE 'UTC') - interval '1 week'` to `date_trunc('week', now() AT TIME ZONE 'UTC') AT TIME ZONE 'UTC'`
- Previous ISO week window: `(date_trunc('week', now() AT TIME ZONE 'UTC') AT TIME ZONE 'UTC') - interval '2 weeks'` to `(date_trunc('week', now() AT TIME ZONE 'UTC') AT TIME ZONE 'UTC') - interval '1 week'`

*(Note: In PostgreSQL, `date_trunc('week', ...)` uses the session time zone; the `AT TIME ZONE 'UTC'` conversions above keep these ISO boundaries at Monday 00:00:00 UTC.)*

## Privacy Guard (ADR-015 & Technical Implementation Plan §54)

All queries and procedures in this runbook enforce strict privacy constraints:

1. **Scalar Aggregates Only:** Every metric query and SQL fallback extracts count, sum, average, percentile, or ratio aggregates.
2. **Strict Media Prohibition:** NEVER query, export, display, log, copy, or paste raw user image bytes, base64 strings, signed S3 URLs, S3 object storage keys, provider prompt payloads, or provider API secrets into runbook records.
3. **Opaque Identifiers Only:** User identifiers appear solely within `COUNT(DISTINCT user_id)` aggregates. Only system-generated UUIDs (`generation_job.id`, `generation_attempt.id`, `share_import.id`) may be inspected for debugging.
4. **Counter Semantics Caveat:** All `product.*` counters emitted by `MicrometerProductMetrics` are **identity-free** and operate on **at-least-once** stream boundaries. They represent event stream counts, NEVER deduplicated unique user counts. Never attempt to derive active user tallies from product counter values.

## 1. Weekly AI Regression Benchmark

### 1.1 Purpose
The weekly AI regression benchmark safeguards virtual try-on (VTON) quality against visual degradation, identity distortion, and latency inflation. It implements plan §52 ("AI Regression Testing") and enforces the binding "No-Demo Rule": no model, prompt, evaluator, or routing modification is promoted to production based on anecdotal demonstrations.

The review operates on two distinct tiers:
1. **Tier 1 (Every Week):** Deterministic offline benchmark test execution to verify test harness, regression comparator, and evaluator wiring integrity.
2. **Tier 2 (Conditional Gate):** Full old-vs-new benchmark comparison executed whenever any plan §52 trigger occurred during the week.

### 1.2 Query & Execution Commands

#### Tier 1 — Weekly Offline Harness Validation (Mandatory Every Week)
Execute the offline regression test suite from the repository root:

```bash
cmd.exe /c mvnw.cmd -Dtest=*Benchmark* test
```

*(On POSIX environments: `./mvnw -Dtest=*Benchmark* test`)*

This command executes in seconds using deterministic offline fake providers (`BenchmarkFakes.ScriptedVtonProvider`), a scripted quality gate (`ScriptedQualityGate`), and a stepped clock. It requires zero network calls, no Docker containers, and no cloud credentials. It confirms:
- Fixture manifest integrity and schema compliance for manifest version `2026.01.0`.
- Comparator determinism and non-inferiority math (`BenchmarkRegressionComparator`).
- Absence of forbidden media markers in serialized reports (`BenchmarkReportJson`).

#### Tier 2 — Mandatory §52 Triggered Old-vs-New Comparison
If ANY of the following five triggers occurred in the repository during the preceding week:
- `provider change`
- `provider version change`
- `prompt change`
- `quality evaluator change`
- `routing change`

the operator MUST execute a candidate-vs-baseline comparison run using `EvaluationBenchmarkRunner` against the standardized benchmark set:
- **Manifest Version:** `2026.01.0` (`backend/src/main/resources/benchmark/manifest.json`).
- **Composition:** 50 synthetic avatars × 100 garment items (Cartesian pairing: 5,000 benchmark cases available; the run spec selects the case set).
- **Category Distribution (seven categories):** tops 22, bottoms 18, dresses 16, kurtas 12, lehenga sets 10, footwear 12, headwear 10.

The operator inspects the six dimensional deltas specified in plan §52:
```text
fidelity
identity
latency
cost
failure rate
quality pass rate
```

The operator records the benchmark run IDs and deltas in `docs/AI_EVALUATION.md`.

**CRITICAL POLICY NOTE:** The benchmark harness and serialized `ReleaseGateDecision` report carry **NO deployment-approval field**. The automated gate produces scalar findings and an advisory verdict (`PASS`, `BLOCK`, or `REVIEW`), but the actual deployment recommendation is a human engineering decision made by the weekly reviewer and recorded in the Section 8 sign-off block.

#### Telemetry Backend & SQL Fallback for Production Quality Monitoring
- **Micrometer Meters:** `generation.quality`, `generation.quality.evaluator.unavailable`, `product.generation.quality_rejection`
- **CloudWatch Alarms:** `<prefix>-ai-quality-collapse`, `<prefix>-p1-quality-reject-ratio`, `<prefix>-p2-category-quality-degraded-<category>`
- **SQL Fallback (Production Quality Gate Outcomes):**

```sql
-- 1. Weekly quality gate decision breakdown and metric averages
SELECT
    COUNT(*) AS total_evaluated,
    COUNT(*) FILTER (WHERE decision = 'PASS') AS quality_pass_count,
    COUNT(*) FILTER (WHERE decision = 'RETRY') AS quality_retry_count,
    COUNT(*) FILTER (WHERE decision = 'FAIL') AS quality_fail_count,
    ROUND(100.0 * COUNT(*) FILTER (WHERE decision = 'PASS') / NULLIF(COUNT(*), 0), 2) AS quality_pass_rate_pct,
    ROUND(100.0 * COUNT(*) FILTER (WHERE decision = 'FAIL') / NULLIF(COUNT(*), 0), 2) AS quality_rejection_rate_pct,
    ROUND(AVG(identity_preservation) FILTER (WHERE decision = 'PASS'), 4) AS avg_identity_fidelity,
    ROUND(AVG(garment_fidelity) FILTER (WHERE decision = 'PASS'), 4) AS avg_garment_fidelity,
    ROUND(AVG(color_fidelity) FILTER (WHERE decision = 'PASS'), 4) AS avg_color_fidelity,
    COUNT(*) FILTER (WHERE artifact_detected = TRUE) AS artifact_detected_count
FROM quality_result
WHERE created_at >= :week_start AND created_at < :week_end;

-- 2. Category-level performance summary from V023 provider performance store
SELECT
    category,
    provider_key,
    model_or_mode,
    SUM(sample_count) AS total_samples,
    SUM(technical_success_count) AS technical_successes,
    SUM(quality_evaluated_count) AS quality_evaluations,
    SUM(quality_approved_count) AS quality_approvals,
    ROUND(100.0 * SUM(quality_approved_count) / NULLIF(SUM(quality_evaluated_count), 0), 2) AS category_pass_rate_pct,
    ROUND(SUM(latency_sum_ms)::NUMERIC / NULLIF(SUM(latency_sample_count), 0), 0) AS avg_latency_ms
FROM generation_provider_performance_daily
WHERE bucket_day >= :week_start::DATE AND bucket_day < :week_end::DATE
GROUP BY category, provider_key, model_or_mode
ORDER BY category, total_samples DESC;
```

### 1.3 Threshold / Expected & Empty-Week Semantics
- **Tier 1 Harness Validation:** 100% tests pass (0 failures, 0 errors, 0 skipped wiring checks).
- **Tier 2 Gate Tolerances (anchored to `ReleaseGateThresholds.defaults()`):**
  - `qualityPassRateFloor`: >= 90.0% candidate quality pass rate (Plan §23 floor).
  - `failRateCeiling`: <= 10.0% overall candidate failure rate.
  - `identityMaxRegressionPercent`: Max 1.0% relative regression in identity preservation.
  - `fidelityMaxRegressionPercent`: Max 2.0% relative regression in overall garment fidelity.
  - `p50CeilingMs`: <= 15,000 ms; `p50MaxRegressionPercent`: <= 5.0% relative increase.
  - `p95CeilingMs`: <= 30,000 ms; `p95MaxRegressionPercent`: <= 10.0% relative increase.
  - `costPerSuccessMaxIncreasePercent`: <= 10.0% relative increase.
- **Empty-Week Semantics:** If zero generation jobs were evaluated or zero benchmark runs were triggered during the week, the section verdict is marked `NO_DATA`. Quality pass rate with a denominator of 0 is mathematically **UNDEFINED** (reported as `NULL`), never 0.0% or 100.0%.

### 1.4 Breach Action & Escalation
- **Tier 1 Failure:** Hard stop. Halt all release pipelines. A failure indicates benchmark harness corruption, fixture manifest invalidity, or comparator breakage. Escalate to Backend Platform Engineer immediately.
- **Tier 2 BLOCK Verdict:** The candidate build is rejected. Deployment to production is strictly forbidden. Escalate to AI Platform Lead and Release Engineer.
- **Tier 2 REVIEW Verdict:** Human adjudication required per statistical guidance in `docs/AI_EVALUATION.md` (Wilson score interval for small samples, Mann-Whitney U test for right-skewed latencies).
- **Production Quality Collapse Alert:** If CloudWatch alarm `<prefix>-ai-quality-collapse` fired during the week (HTTP 200 normal, but quality pass rate collapsed per §69), cross-reference with Section 2 and invoke §66 remote feature-flag kill-switches (`TRYON_MAX=false` or `NEW_QUALITY_GATE=false`) if persistent drift is detected.

## 2. Review Failed Generations

### 2.1 Purpose
The failed-generations review analyzes technical generation reliability across the completed week. It separates transport and infrastructure failures from visual quality gate rejections, tracks retry exhaustion patterns, and identifies provider-side instability or rate-limiting.

### 2.2 Query & Measurement Surfaces
- **Micrometer Meters:**
  - `generation.terminal` (tags: `category` with values `COMPLETED`, `FAILED`, `CANCELLED`, `SUBJECT_DELETED`, `BUDGET_EXHAUSTED`, `DEADLINE_EXPIRED`, `UNKNOWN`)
  - `generation.retry.exhaustion` (counter of terminal jobs exhausting retry budget)
  - `generation.retry.provider.outcomes` (tags: `category` with values `PROVIDER_TIMEOUT`, `PROVIDER_RATE_LIMIT`, `PROVIDER_INTERNAL_ERROR`, `PROVIDER_NON_RETRYABLE`, `UNKNOWN`)
  - `generation.transition` (job state machine transitions)
  - `generation.queue_wait` (timer tracking queue dispatch delay)
  - `generation.outbox.lag` (gauge tracking transactional outbox polling lag)
  - `product.generation.success` (parts `numerator`, `denominator` — identity-free, at-least-once)
  - `product.generation.quality_rejection`
  - `product.generation.latency` (distribution of end-to-end generation durations)
  - `generation.count`, `generation.latency`, `generation.provider_latency`
  - `provider.attempts`, `provider.error`, `provider.credit_balance`
- **CloudWatch Alarms:** `<prefix>-p0-generation-failure-ratio`, `<prefix>-p1-provider-errors`, `<prefix>-p1-quality-reject-ratio`, `<prefix>-p1-provider-credits-low`
- **SQL Fallback (Read-Only PostgreSQL):**

```sql
-- 1. Weekly generation job terminal status and WoW technical success comparison
WITH current_week AS (
    SELECT
        COUNT(*) AS total_jobs,
        COUNT(*) FILTER (WHERE status = 'COMPLETED') AS completed_jobs,
        COUNT(*) FILTER (WHERE status = 'FAILED') AS failed_jobs,
        COUNT(*) FILTER (WHERE status NOT IN ('COMPLETED', 'FAILED')) AS incomplete_jobs,
        ROUND(100.0 * COUNT(*) FILTER (WHERE status = 'COMPLETED') / NULLIF(COUNT(*) FILTER (WHERE status IN ('COMPLETED', 'FAILED')), 0), 2) AS tech_success_rate_pct
    FROM generation_job
    WHERE created_at >= :week_start AND created_at < :week_end
),
prev_week AS (
    SELECT
        COUNT(*) AS prev_total_jobs,
        COUNT(*) FILTER (WHERE status = 'COMPLETED') AS prev_completed_jobs,
        COUNT(*) FILTER (WHERE status = 'FAILED') AS prev_failed_jobs,
        ROUND(100.0 * COUNT(*) FILTER (WHERE status = 'COMPLETED') / NULLIF(COUNT(*) FILTER (WHERE status IN ('COMPLETED', 'FAILED')), 0), 2) AS prev_tech_success_rate_pct
    FROM generation_job
    WHERE created_at >= :prev_week_start AND created_at < :prev_week_end
)
SELECT
    c.total_jobs,
    c.completed_jobs,
    c.failed_jobs,
    c.incomplete_jobs,
    c.tech_success_rate_pct,
    p.prev_tech_success_rate_pct,
    ROUND(c.tech_success_rate_pct - p.prev_tech_success_rate_pct, 2) AS wow_delta_pct_points
FROM current_week c CROSS JOIN prev_week p;

-- 2. Attempt-level failure code taxonomy and retry exhaustion breakdown
SELECT
    provider,
    COALESCE(failure_code, 'SUCCESS') AS failure_code,
    technical_outcome,
    COUNT(*) AS attempt_count,
    COUNT(DISTINCT generation_job_id) AS distinct_jobs_affected,
    ROUND(AVG(latency_ms), 0) AS avg_latency_ms
FROM generation_attempt
WHERE started_at >= :week_start AND started_at < :week_end
GROUP BY provider, failure_code, technical_outcome
ORDER BY attempt_count DESC;

-- 3. Retry exhaustion analysis: jobs terminated by persisted retry-exhaustion terminal reasons
--    (excludes cancelled, deadline-exceeded, and cost-blocked terminals, which are not user-facing retry exhaustion;
--     per-job attempt ceiling = total_steps + 2 per GenerationRetryBudget, so terminal_reason is the authoritative signal)
SELECT
    gj.id AS job_id,
    gj.status,
    gj.terminal_reason,
    COUNT(ga.id) AS attempts_executed,
    STRING_AGG(DISTINCT ga.failure_code, ', ') AS observed_failure_codes
FROM generation_job gj
JOIN generation_attempt ga ON ga.generation_job_id = gj.id
WHERE gj.created_at >= :week_start AND gj.created_at < :week_end
  AND gj.status = 'FAILED'
  AND gj.terminal_reason IN (
      'RETRY_BUDGET_EXHAUSTED',
      'QUALITY_RETRY_EXHAUSTED',
      'PROVIDER_TIMEOUT_EXHAUSTED',
      'PROVIDER_RATE_LIMIT_EXHAUSTED',
      'PROVIDER_QUOTA_EXHAUSTED'
  )
GROUP BY gj.id, gj.status, gj.terminal_reason;

-- 4. Weekly quality outcome breakdown: separates visual-quality rejections from transport failures
--    (join generation_attempt to quality_result per spec decision 5; fills the Section 2 sign-off Quality Rejection Rate field)
SELECT
    COUNT(*) AS evaluated_attempts,
    COUNT(*) FILTER (WHERE qr.decision = 'PASS') AS quality_pass_count,
    COUNT(*) FILTER (WHERE qr.decision = 'FAIL') AS quality_fail_count,
    ROUND(100.0 * COUNT(*) FILTER (WHERE qr.decision = 'PASS') / NULLIF(COUNT(*), 0), 2) AS quality_pass_rate_pct,
    ROUND(100.0 * COUNT(*) FILTER (WHERE qr.decision = 'FAIL') / NULLIF(COUNT(*), 0), 2) AS quality_rejection_rate_pct,
    ROUND(AVG(qr.identity_preservation) FILTER (WHERE qr.decision = 'PASS'), 4) AS avg_identity_fidelity,
    ROUND(AVG(qr.garment_fidelity) FILTER (WHERE qr.decision = 'PASS'), 4) AS avg_garment_fidelity,
    ROUND(AVG(qr.color_fidelity) FILTER (WHERE qr.decision = 'PASS'), 4) AS avg_color_fidelity,
    COUNT(*) FILTER (WHERE qr.artifact_detected = TRUE) AS artifact_detected_count
FROM quality_result qr
JOIN generation_attempt ga ON ga.id = qr.generation_attempt_id
WHERE qr.created_at >= :week_start AND qr.created_at < :week_end;
```

### 2.3 Threshold / Expected & Empty-Week Semantics
- **Technical Success Rate Target:** > 95.0% (tied to technical implementation plan §65 beta exit gate: "Technical generation > 95%").
- **Quality Rejection Rate Target:** < 10.0% (tied to plan §65 gate: "Quality rejection < 10%").
- **Week-over-Week Delta:** Relative increase in failure rate must not exceed ±20% relative tolerance compared to previous week.
- **Retry Exhaustion Ceiling:** Retry-exhausted jobs must represent < 1.0% of total jobs.
- **Empty-Week Semantics:** If `total_jobs = 0`, report `NO_DATA`. Rates with zero denominators are **UNDEFINED** (`NULL`).

### 2.4 Breach Action & Escalation
- **Technical Success < 90.0% or Failure Surge > 20% WoW:** Severity P1 incident. Escalate to Generation Worker On-Call Engineer.
  - If `PROVIDER_TIMEOUT` or `PROVIDER_RATE_LIMIT` dominates, check provider status page, inspect rate limiter configuration, and check outbound NAT gateway saturation.
  - If `PROVIDER_INTERNAL_ERROR` dominates, open ticket with provider support and consider failover via provider routing configuration.
  - If gauge `provider.credit_balance` indicates low prepaid credits or `<prefix>-p1-provider-credits-low` fired, escalate to FinOps to replenish credit reserves immediately.
- **Quality Rejection Spikes > 10.0%:** Severity P1. Escalate to AI Platform Lead. Cross-check with Section 1 and `<prefix>-ai-quality-collapse`.

## 3. Review Source-Import Compatibility

### 3.1 Purpose
The source-import compatibility review monitors share ingestion reliability across external sources (Android share target, iOS share extension, browser shares) and specific e-commerce retailer domains. Because retailer website layouts change without notice and anti-bot measures evolve, this review isolates per-source degradation before global metrics reflect user frustration.

### 3.2 Query & Measurement Surfaces
- **Micrometer Meters:**
  - `product.share.import.success` (parts `numerator`, `denominator` — identity-free, at-least-once)
  - `product.share.try_on` (share import conversion to try-on)
  - `share.import.resolver.outcome` (tags: `resolver` with values `SHARED_IMAGE`, `GENERIC_OPEN_GRAPH`, `GENERIC_URL`; `status` with values `RESOLVED`, `NEEDS_IMAGE`, `RETRYABLE_FAILURE`, `TERMINAL_FAILURE`, `UNSUPPORTED`, `EXCEPTION`; `reason` with values `URL_RESOLUTION_FAILED`, `DEPENDENCY_UNAVAILABLE`, `RESOLUTION_TIMEOUT`, `INVALID_SOURCE`, `NONE`)
  - `share.import.resolver.duration` (tags: `resolver`, `status`)
- **CloudWatch Alarms:** `<prefix>-p2-import-resolver-degraded-<resolver>` (alarm set keyed by resolver id from `var.source_resolver_ids`; current Terraform selects `status = TERMINAL_FAILURE` via `var.resolver_failure_status` and also counts `EXCEPTION` in the failure numerator, with failure-ratio threshold `var.p2_resolver_failure_ratio`, default 0.25, over 3 of 6 hours; applied AWS state is not verified by this runbook)
- **SQL Fallback (Read-Only PostgreSQL):**

```sql
-- 1. Weekly import resolution volume, success rate, and terminal failure breakdown
SELECT
    COUNT(*) AS total_imports,
    COUNT(*) FILTER (WHERE resolver_state = 'READY') AS successful_imports,
    COUNT(*) FILTER (WHERE resolver_state = 'NEEDS_IMAGE') AS needs_image_imports,
    COUNT(*) FILTER (WHERE resolver_state = 'RESOLVING') AS in_flight_imports,
    COUNT(*) FILTER (WHERE resolver_state = 'FAILED_RETRYABLE') AS retryable_failures,
    COUNT(*) FILTER (WHERE resolver_state = 'FAILED_TERMINAL') AS terminal_failures,
    ROUND(100.0 * COUNT(*) FILTER (WHERE resolver_state = 'READY') / NULLIF(COUNT(*), 0), 2) AS success_rate_pct,
    ROUND(100.0 * COUNT(*) FILTER (WHERE resolver_state = 'FAILED_TERMINAL') / NULLIF(COUNT(*), 0), 2) AS terminal_failure_pct
FROM share_import
WHERE created_at >= :week_start AND created_at < :week_end;

-- 2. Per-source-site resolution outcome breakdown
SELECT
    COALESCE(si.source_site_name, 'UNKNOWN') AS source_site,
    si.source_kind,
    COUNT(*) AS total_shares,
    COUNT(*) FILTER (WHERE si.resolver_state = 'READY') AS resolved_ready,
    COUNT(*) FILTER (WHERE si.resolver_state = 'NEEDS_IMAGE') AS fallback_needs_image,
    COUNT(*) FILTER (WHERE si.resolver_state = 'FAILED_TERMINAL') AS terminal_failures,
    ROUND(100.0 * COUNT(*) FILTER (WHERE si.resolver_state = 'READY') / NULLIF(COUNT(*), 0), 2) AS resolution_success_rate_pct,
    ROUND(100.0 * COUNT(*) FILTER (WHERE si.resolver_state = 'FAILED_TERMINAL') / NULLIF(COUNT(*), 0), 2) AS failure_rate_pct,
    MODE() WITHIN GROUP (ORDER BY si.terminal_reason_code) AS leading_terminal_reason
FROM share_import si
WHERE si.created_at >= :week_start AND si.created_at < :week_end
GROUP BY source_site, si.source_kind
HAVING COUNT(*) >= 5
ORDER BY failure_rate_pct DESC, total_shares DESC;
```

*Schema note:* Retailer-level correlation is not persisted on share_import (the FK lives on vault_item), so source_site_name is the per-source surface.

*Vocabulary note:* Valid `resolver_state` values are `RESOLVING`, `READY`, `NEEDS_IMAGE`, `FAILED_RETRYABLE`, `FAILED_TERMINAL`, `DELETED`. Valid `terminal_reason_code` values are `URL_RESOLUTION_FAILED`, `DEPENDENCY_UNAVAILABLE`, `RESOLUTION_TIMEOUT`, `INVALID_SOURCE`.

### 3.3 Threshold / Expected & Empty-Week Semantics
- **Global Import Success Rate Target:** > 90.0% (tied to plan §65 beta exit gate: "Import success > 90%").
- **P2 Resolver Alarm Threshold:** The landed CloudWatch alarm `<prefix>-p2-import-resolver-degraded-<resolver>` evaluates `TERMINAL_FAILURE` plus `EXCEPTION` outcome counts for each resolver id over 3 of 6 hours (failure ratio >= 0.25, default `var.p2_resolver_failure_ratio`); applied alarm state remains unverified.
- **Per-Source Degraded Review Rule (Runbook Review Rule):** As a runbook review rule (evaluated via SQL fallback over `share_import.source_site_name`, not an automated alarm condition), any major source domain with volume >= 20 exhibiting failure rate > 30.0% (success rate < 70.0%) requires investigation.
- **Week-over-Week Delta:** Relative change in per-source success rate must not drop by > 10.0% relative WoW.
- **Empty-Week Semantics:** If `total_imports = 0`, mark `NO_DATA`; rates are **UNDEFINED** (`NULL`).

### 3.4 Breach Action & Escalation
- **Resolver Degraded (P2 Alarm Firing or Review Rule Breach):** Severity P2. Escalate to Integrations / Backend On-Call Engineer when the resolver P2 alarm fires (failure ratio >= 0.25) or when runbook review identifies a major source domain with failure rate > 30% on volume >= 20.
  - Confirm or clear active `<prefix>-p2-import-resolver-degraded-<resolver>` CloudWatch alarm.
  - Inspect sample retailer product pages to identify changes in OpenGraph tags (`og:image`), structured JSON-LD data, or HTTP 403 bot challenges.
  - If anti-bot defenses block URL resolution, verify that `NEEDS_IMAGE` fallback triggers gracefully, prompting users to provide a screenshot or image directly.
- **Global Import Success Rate < 85.0%:** Severity P1. Escalate to Backend Lead. If platform-specific, invoke §66 feature flag kill-switch `SHARE_IMPORT_ANDROID=false` or `SHARE_IMPORT_IOS=false` to protect the mobile user experience.

## 4. Review Vault Reuse

### 4.1 Purpose
The Vault reuse review evaluates user engagement with saved wardrobe assets over time. Technical implementation plan §0 establishes the core product loop: `SHARE → RESOLVE → TRY ON → QUALITY CHECK → LOOK → VAULT → STUDIO`. This review verifies whether the Vault serves as a living, reusable wardrobe or suffers from one-time churn.

### 4.2 Query & Measurement Surfaces
- **Micrometer Meters:**
  - `product.vault.reuse` (parts: `numerator` for `VAULT_ITEM_REUSED`, `denominator` for `VAULT_ITEM_CREATED` — identity-free stream boundaries, at-least-once counter semantics)
  - `product.vault.items` (total active items in personal vaults)
- **SQL Fallback (Read-Only PostgreSQL):**

```sql
-- 1. Weekly Vault item creations, reuse events, and aggregate reuse ratio
WITH weekly_creations AS (
    SELECT
        COUNT(*) AS items_created_this_week
    FROM vault_item
    WHERE created_at >= :week_start AND created_at < :week_end
),
weekly_reuses AS (
    -- Items referenced in studio sessions created during the week, or in looks generated during the week
    --    (look_item persists reuse for both Studio and non-Studio looks; look.studio_session_id is nullable per V008)
    SELECT
        COUNT(DISTINCT reused.vault_item_id) AS items_reused_this_week
    FROM (
        SELECT si.vault_item_id
        FROM studio_item si
        JOIN studio_session ss ON ss.id = si.studio_session_id
        WHERE ss.created_at >= :week_start AND ss.created_at < :week_end
        UNION
        SELECT li.vault_item_id
        FROM look_item li
        JOIN look l ON l.id = li.look_id
        WHERE l.created_at >= :week_start AND l.created_at < :week_end
    ) reused
)
SELECT
    c.items_created_this_week,
    r.items_reused_this_week,
    ROUND(100.0 * r.items_reused_this_week / NULLIF(c.items_created_this_week, 0), 2) AS weekly_reuse_ratio_pct
FROM weekly_creations c CROSS JOIN weekly_reuses r;

-- 2. Category distribution of active Vault inventory
SELECT
    category,
    COUNT(*) AS total_items,
    ROUND(100.0 * COUNT(*) / SUM(COUNT(*)) OVER (), 2) AS category_share_pct
FROM vault_item
GROUP BY category
ORDER BY total_items DESC;
```

*Counter Semantics Caveat:* Per `MicrometerProductMetrics` design, the reuse ratio uses items created (`VAULT_ITEM_CREATED`) as its denominator. It does not measure unique user ratios.

### 4.3 Threshold / Expected & Empty-Week Semantics

- **Absolute Targets:** Absolute engagement floors are deferred to closed-beta data per technical implementation plan §65 ("Retention targets should be derived from real beta data"). Initial engineering baseline expectation is 15.0% - 40.0% weekly reuse.
- **Empty-Week Semantics:** If `items_created_this_week = 0`, report `NO_DATA`; reuse ratio is **UNDEFINED** (`NULL`).

## 5. Review Studio Usage

### 5.1 Purpose
The Studio usage review monitors engagement with the deterministic outfit composition canvas (plan §33–36). It tracks Studio session volume, multi-item try-on adoption, and conversion from outfit generation to saved and shared Looks.

Per ADR-011 ("Deterministic Studio State"), this operational review is strictly **read-only**: it inspects structured slots and render plans, never mutates state, and enforces that LLM tool-calling remains layered above application services.

### 5.2 Query & Measurement Surfaces
- **Micrometer Meters:**
  - `product.studio.usage` (parts: `numerator` = Studio-mode generations, `denominator` = `STUDIO_STARTED` events)
  - `product.generation.multi_item` (numerator = generations with 2+ outfit items)
  - `product.look.save` (Looks saved to user profile)
  - `product.look.share` (Looks shared externally)
- **SQL Fallback (Read-Only PostgreSQL):**

```sql
-- 1. Weekly Studio sessions, studio-originated generations, and multi-item mix
WITH studio_generations AS (
    SELECT
        gj.id AS job_id,
        gj.studio_session_id,
        COUNT(si.id) AS slot_items_count
    FROM generation_job gj
    LEFT JOIN studio_item si ON si.studio_session_id = gj.studio_session_id
    WHERE gj.created_at >= :week_start AND gj.created_at < :week_end
      AND gj.studio_session_id IS NOT NULL
    GROUP BY gj.id, gj.studio_session_id
)
SELECT
    (SELECT COUNT(*) FROM studio_session WHERE created_at >= :week_start AND created_at < :week_end) AS total_studio_sessions,
    COUNT(job_id) AS total_studio_generations,
    COUNT(job_id) FILTER (WHERE slot_items_count > 1) AS multi_item_generations,
    ROUND(100.0 * COUNT(job_id) FILTER (WHERE slot_items_count > 1) / NULLIF(COUNT(job_id), 0), 2) AS multi_item_generation_pct
FROM studio_generations;

-- 2. Look conversion: save volume and save rate (look row existence is the save event; share rate is tracked via the product.look.share counter)
--    (save-rate denominator = completed generation jobs, matching the product.look.save counter contract:
--     LOOK_SAVED is the numerator and GENERATION_COMPLETED the denominator)
SELECT
    (SELECT COUNT(*) FROM look WHERE created_at >= :week_start AND created_at < :week_end) AS total_looks_saved,
    (SELECT COUNT(*) FROM generation_job WHERE created_at >= :week_start AND created_at < :week_end AND status = 'COMPLETED') AS completed_generations,
    ROUND(
        100.0 * (SELECT COUNT(*) FROM look WHERE created_at >= :week_start AND created_at < :week_end)
        / NULLIF((SELECT COUNT(*) FROM generation_job WHERE created_at >= :week_start AND created_at < :week_end AND status = 'COMPLETED'), 0),
        2
    ) AS look_save_rate_pct;
```

- **Absolute Targets:** Deferred to beta data per §65. Expected beta operating ranges: multi-item generation share 20.0% - 45.0%; Look save rate > 30.0%.
- **Empty-Week Semantics:** If `total_studio_sessions = 0`, report `NO_DATA`; conversion rates are **UNDEFINED** (`NULL`).

- **Studio Usage or Multi-Item Share Drops > 20% WoW:** Severity P2 / Product Advisory. Escalate to Mobile Client Lead and AI Platform Lead.

## 6. Review Retention

### 6.1 Purpose
The retention review audits user engagement retention offsets (Day 1, Day 7, Day 30), time-to-first-look activation speed, and the operational execution of ephemeral storage lifecycle cleanup jobs.

This section operationalizes plan §49 ("Data Retention"):
- Temporary generation inputs, failed intermediates, and import staging assets MUST be deleted within 24 hours.
- User-controlled persistent assets (My Model, Vault items, Saved Looks) remain indefinitely until explicit user deletion.
- Background scheduled cleanup jobs must execute with zero silent failures.

### 6.2 Query & Measurement Surfaces
- **Micrometer Meters:**
  - `product.retention` (tags: `offset1`, `offset7`, `offset30`; parts: `numerator`, `denominator` — identity-free stream boundaries)
  - `product.time_to_first_look` (Timer distribution measuring latency from account activation to first completed Look)
  - `product.core.quality_approved_looks_per_activated_user_week` (ISO-week tagged `w%04d-%02d`, parts `numerator`/`denominator`)
  - `generation.orphan.cleanup` (counter of orphaned storage objects purged)
- **Verified Background Retention Jobs:**
  - Hourly temp cleanup: `ObjectStoreConfiguration.TempCleanup`
  - Generation orphan sweeper (24h safe age): `platform/objectstore/GenerationOrphanSweeper.java`
  - Avatar orphan cleanup: `avatar/AvatarCleanupConfiguration ScheduledCleanup`
  - Privacy deletion purge handlers: Flyway V021 account deletion lifecycle
- **SQL Fallback (Read-Only PostgreSQL):**

*Fallback table note:* the time-to-first-look cohort query reads `users` (aggregate-only: account-creation week join; final output is scalar percentiles with no per-user rows, per the Privacy Guard). `users.created_at` is the only account-creation surface in the schema, so it is deliberately admitted to this runbook's fallback set.

```sql
-- 1. Weekly new activated user cohorts and first-look timing (derived from look creation history)
WITH user_first_looks AS (
    SELECT
        u.id AS user_id,
        u.created_at AS user_created_at,
        MIN(l.created_at) AS first_look_created_at
    FROM users u
    JOIN look l ON l.user_id = u.id
    WHERE u.created_at >= :week_start AND u.created_at < :week_end
    GROUP BY u.id, u.created_at
)
SELECT
    COUNT(*) AS activated_users_cohort,
    ROUND(AVG(EXTRACT(EPOCH FROM (first_look_created_at - user_created_at))), 0) AS avg_time_to_first_look_sec,
    ROUND(PERCENTILE_CONT(0.50) WITHIN GROUP (ORDER BY EXTRACT(EPOCH FROM (first_look_created_at - user_created_at))), 0) AS p50_time_to_first_look_sec,
    ROUND(PERCENTILE_CONT(0.95) WITHIN GROUP (ORDER BY EXTRACT(EPOCH FROM (first_look_created_at - user_created_at))), 0) AS p95_time_to_first_look_sec
FROM user_first_looks;

-- 2. Compliance Audit: Verify no temporary generation records linger past 24h safe age (§49)
SELECT
    COUNT(*) AS lingering_temp_records_past_24h
FROM generation_job
WHERE created_at < NOW() - INTERVAL '24 hours'
  AND status IN ('QUEUED', 'PREFLIGHT', 'SUBMITTED', 'GENERATING', 'QUALITY_CHECK', 'RETRYING')
  AND updated_at < NOW() - INTERVAL '24 hours';
```

### 6.3 Threshold / Expected & Empty-Week Semantics
- **Week-over-Week Retention Delta:** Relative changes in D1/D7 retention rates must remain within ±20% relative tolerance. Absolute retention floors are deferred to beta data per §65.
- **Storage Hygiene Compliance Target:** `lingering_temp_records_past_24h = 0`. Exactly zero temporary generation records or staged assets may exceed the 24-hour retention ceiling without an active sweep lock.
- **Empty-Week Semantics:** If `activated_users_cohort = 0`, report `NO_DATA`; retention rates are **UNDEFINED** (`NULL`).

  - Manually trigger `GenerationOrphanSweeper` and `ObjectStoreConfiguration.TempCleanup`.
  - Check S3 bucket lifecycle configuration and ECS task scheduler status.

## 7. Review Generation Cost

### 7.1 Purpose
The generation cost review audits AI cloud economics and unit profitability. Plan §43 ("Cost Metrics") and ADR-014 ("Provider cost stored per generation") mandate that every generation attempt records its actual or estimated provider cost, currency, and billing units.

The headline economic indicator is:
> **Cost per Quality-Approved Look** (`product.look.cost.quality_approved`)

Unlike simple cost-per-request metrics, this indicator accounts for retries, fallen transport attempts, and quality gate rejections, reflecting the true cost to deliver a satisfactory user output.

### 7.2 Query & Measurement Surfaces
- **Micrometer Meters:**
  - `product.look.cost.quality_approved` (headline distribution, part `amount` — includes retried/rejected spend)
  - `product.look.cost.success` (cost per technically successful look)
  - `generation.cost`, `generation.cost.attempt`, `generation.cost.amount`
  - `product.core.quality_approved_looks_per_activated_user_week` (ISO-week tagged `w%04d-%02d`)
  - `provider.credit_balance` (provider account credit gauge)
- **CloudWatch Alarms:** `<prefix>-p1-generation-cost-hourly`, `<prefix>-p1-provider-credits-low`
- **SQL Fallback (Read-Only PostgreSQL):**

```sql
-- 1. Weekly provider spend, approved Looks count, and Cost per Quality-Approved Look
WITH attempt_spend AS (
    SELECT
        COUNT(*) AS total_attempts,
        CASE
            WHEN COUNT(*) FILTER (WHERE cost_status = 'UNKNOWN') > 0
              OR COUNT(*) FILTER (WHERE cost_status IS NULL) > 0
              OR COUNT(DISTINCT currency) FILTER (WHERE cost_status IN ('FINAL', 'ESTIMATED')) > 1
              OR COUNT(*) FILTER (
                  WHERE cost_status IN ('FINAL', 'ESTIMATED')
                    AND ((cost_status = 'FINAL' AND (actual_cost IS NULL OR currency IS NULL))
                      OR (cost_status = 'ESTIMATED' AND (estimated_cost IS NULL OR currency IS NULL)))
              ) > 0
            THEN NULL
            ELSE SUM(
                CASE
                    WHEN cost_status = 'FINAL' AND actual_cost IS NOT NULL AND currency IS NOT NULL THEN actual_cost
                    WHEN cost_status = 'ESTIMATED' AND estimated_cost IS NOT NULL AND currency IS NOT NULL THEN estimated_cost
                END
            )
        END AS total_spend,
        COUNT(*) FILTER (WHERE cost_status = 'FINAL') AS final_cost_attempts,
        COUNT(*) FILTER (WHERE cost_status = 'ESTIMATED') AS estimated_cost_attempts,
        COUNT(*) FILTER (WHERE cost_status = 'UNKNOWN') AS unknown_cost_attempts
    FROM generation_attempt ga
    WHERE ga.started_at >= :week_start AND ga.started_at < :week_end
),
approved_looks AS (
    SELECT COUNT(DISTINCT l.id) AS quality_approved_looks_count
    FROM look l
    JOIN generation_job gj ON gj.id = l.generation_job_id AND gj.user_id = l.user_id
    JOIN generation_attempt ga
      ON ga.generation_job_id = gj.id
     AND split_part(l.storage_key, '/', 4) LIKE ga.id::text || '.%'
    JOIN quality_result qr ON qr.generation_attempt_id = ga.id
    WHERE l.created_at >= :week_start AND l.created_at < :week_end
      AND l.deleted_at IS NULL
      AND l.quality_status = 'PASS'
      AND gj.status = 'COMPLETED'
      AND ga.technical_outcome = 'SUCCESS'
      AND qr.decision = 'PASS'
)
SELECT
    s.total_attempts,
    s.total_spend AS weekly_spend_total,
    l.quality_approved_looks_count,
    ROUND(
        s.total_spend::NUMERIC /
        NULLIF(l.quality_approved_looks_count, 0),
        4
    ) AS cost_per_quality_approved_look,
    ROUND(100.0 * s.unknown_cost_attempts / NULLIF(s.total_attempts, 0), 2) AS unknown_cost_status_pct
FROM attempt_spend s CROSS JOIN approved_looks l;

-- 2. Provider economics and cost status breakdown
SELECT
    provider,
    model,
    currency,
    cost_status,
    COUNT(*) AS attempts_count,
    ROUND(SUM(
        CASE
            WHEN cost_status = 'FINAL' AND actual_cost IS NOT NULL AND currency IS NOT NULL THEN actual_cost
            WHEN cost_status = 'ESTIMATED' AND estimated_cost IS NOT NULL AND currency IS NOT NULL THEN estimated_cost
        END
    )::NUMERIC, 2) AS total_spend,
    ROUND(AVG(
        CASE
            WHEN cost_status = 'FINAL' AND actual_cost IS NOT NULL AND currency IS NOT NULL THEN actual_cost
            WHEN cost_status = 'ESTIMATED' AND estimated_cost IS NOT NULL AND currency IS NOT NULL THEN estimated_cost
        END
    )::NUMERIC, 4) AS avg_cost_per_attempt
FROM generation_attempt
WHERE started_at >= :week_start AND started_at < :week_end
GROUP BY provider, model, currency, cost_status
ORDER BY total_spend DESC;
```

Vocabulary note: Valid `cost_status` values in `generation_attempt` are `ESTIMATED`, `FINAL`, and `UNKNOWN`; a NULL `cost_status` is malformed accounting state and fails closed.
The Look storage key is generated from the publishing attempt UUID, so the join above accepts only the publishing attempt's PASS result; an unrelated retry cannot approve the Look. UNKNOWN or NULL costs remain `NULL`, never zero.

### 7.3 Threshold / Expected & Empty-Week Semantics
- **Cost per Quality-Approved Look WoW Delta:** Relative increase must not exceed ±20% relative tolerance compared to the prior week.
- **Cost Status UNKNOWN Ceiling:** Attempts with `cost_status = 'UNKNOWN'` must represent < 2.0% of total weekly attempts.
  - Amber Band: 2.0% - 5.0% UNKNOWN.
  - Red Breach Band: > 5.0% UNKNOWN (classified as a telemetry and accounting failure).
- **Provider Credit Buffer:** Provider credit balance must represent > 3 days of projected burn (tied to `<prefix>-p1-provider-credits-low`).
- **Empty-Week Semantics:** If `quality_approved_looks_count = 0`, report `NO_DATA`; Cost per Quality-Approved Look is **UNDEFINED** (`NULL`), never 0.0 or infinity.

### 7.4 Breach Action & Escalation
- **Cost per Approved Look Increases > 20% WoW:** Severity P1. Escalate to FinOps On-Call and AI Platform Lead.
  - Check whether provider pricing changed without notice.
  - Check whether retry rate (Section 2) or quality rejection rate (Section 1) spiked, inflating the attempts required per approved Look.
  - If budget depletion threatens global margins, invoke plan §75 cost circuit breakers (restrict multi-item generations, disable high-definition modes).
- **Unknown Cost Share > 5.0%:** Severity P2 Data Quality Defect. Escalate to Backend Platform Engineer to repair provider billing response parser.
